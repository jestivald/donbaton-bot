## 2. Что принесли релизы

### 2.1 v4.14.0 (54 файла, +2317/−117)

* **«Старая подписка» — платная, без тарифа, при включённых тарифах**
  (`app/utils/legacy_subscription.py:18`). Продления и автоплатежа у неё нет, докупки
  отклоняются в боте и в кабинете, в меню одна кнопка «📦 Перейти на тариф». Для нас это
  главный пункт релиза — **§6**.
* **Одно правило «создавать аккаунт панели или обновлять свой»**
  (`panel_sync/identity.py:380::should_create_panel_account`) — во всех точках покупки, смены
  и продления тарифа вместо `not user.remnawave_id`. В одиночном режиме (он у нас) разница
  одна: человек без `users.remnawave_id`, у подписки которого id есть и не занят другим,
  получает этот id и обновление, а не второй аккаунт. Функция сама делает `db.commit()`.
* Аккаунт, созданный в мультитарифе, пишется и человеку (`users.remnawave_id`), если там
  пусто и id свободен (`user_panel_id_is_free_for`, `identity.py:349`). Плюс разовый бэкфил
  миграцией — у нас `0127` (§7).
* **Сегменты «Пользователей» считаются по подписке**, а не по сырому статусу
  (`app/database/crud/subscription_segments.py`): триалы — свой сегмент, «истекают» — только
  платные. Плитки статистики и выборки кабинета дадут другие числа — данные те же.

## 4. Панель и теги

**Теги — без изменений с 4.13.0.** `panel_sync/payload.py` и `panel_sync/tags.py` релизы не
трогали: бот по-прежнему всегда пишет `tag`, пустой снимает ручной. **Правило из handoff 4.13.0
§5 в силе: «Из бота в панель» не нажимать, пока не заданы `tariffs.panel_tag` /
`PAID_SUBSCRIPTION_USER_TAG` / `TRIAL_USER_TAG`** (жёсткое правило проекта).

Что поменялось в работе с панелью:

* **Запись связи с мёртвым id (#3277).** `resolve_panel_identity` запоминает записанные id,
  которых панель не нашла (`dead_recorded_ids`); `_record_identity` их затирает. Если PATCH
  ответил «такого пользователя нет», `push_subscription` сначала ищет аккаунт подписки другими
  ключами (`shortUuid`, Telegram, почта) и **перепривязывает найденный** вместо создания
  дубля (`writer.py:171`), только потом создаёт.
* **Снимок панели не укорачивает срок 48 ч после оплаты** (`projection.py:57`
  `PAID_DATE_HOLD`, `:314 panel_date_behind_paid_renewal`). Вебхук, сверка и мониторинг
  истечения передают время последней оплаты подписки (`crud/transaction.py
  ::get_last_subscription_payment_at`); более ранняя дата панели не принимается, статус
  «истекла», выведенный из неё, тоже; вебхук ставит в очередь повторную запись срока бота в
  панель (`remnawave_webhook_service.py:1376`). **Для оператора:** укоротить свежеоплаченную
  подписку правкой даты в панели в эти 48 ч не выйдет — бот вернёт свой срок. Подписок
  Wi-Fi/LTE это не меняет: у них дату и так ведёт бот (`takes_date=False`).
* **«Удалил подписку и купил заново»** не наследует удалённый аккаунт
  (`subscription_deletion_service`: при настоящем удалении аккаунта снимается и
  `users.remnawave_id`).
* **Сверка карточки** в кабинете показывает расхождение «В панели аккаунт не найден», а
  «в панель» больше не ставит отметку синхронизации, если связь не обновилась.
* **Производительность:** +1 `SELECT max(created_at) FROM transactions …` на подписку в
  проходах синхронизации, вебхуке и мониторинге истечения (ради `PAID_DATE_HOLD`).

Наш шов не задет: политика Wi-Fi/LTE по-прежнему накладывается один раз в начале
`push_subscription` (`writer.py:132`), досылка после создания аккаунта — на обоих путях
создания (`writer.py:231`, `:286`). Наш admin-sync fallback `_adoptable_user_panel_id`
(4 ссылки) на месте и дополняет апстримовский `should_create_panel_account`: тот работает в
покупках, наш — в админском «продлить/в панель» выбранной подписки.

  выдать дизайнеру отдельную несистемную роль до выкладки. Решение — за владельцем.

### 5.2 Напоминания о заявках на вывод

### 5.3 Уведомления о старте и остановке

Стартовое — новый формат (сводка по разделам, «требует внимания»). Остановка — новое:
`main.py` ловит сигнал и за ≤5 с шлёт в админ-чат причину и аптайм

«остановка / запуск»** — владельцу стоит знать заранее.

### 5.4 Промогруппы

* Клиент получает сообщение об автоназначении группы за траты — по умолчанию включено.
* При создании группы с порогом, смене порога и удалении группы (если пороги ещё есть)
  запускается фоновый пересчёт по всем, у кого есть траты (`promo_group_recalculation.py`);
  есть кнопка `POST /cabinet/admin/promo-groups/recalculate`. Массовый пересчёт клиентам не
  пишет, админам — одну сводку. **Если у наших групп есть пороги**, правка групп после выкладки
  может разом поменять скидки многим людям — проверить SQL в §11.

### 5.5 Платежи

* **Покупка тарифа в кабинете** (`purchase.py`, правило `traffic_reset_policy.py
  ::should_reset_traffic_on_tariff_purchase`): после триала — обнулять всегда; смена тарифа —
  по общему правилу переключений; продление того же тарифа — по `RESET_TRAFFIC_ON_PAYMENT`.
  Раньше панель обнулялась литералом при любой оплате. Для подписок Wi-Fi/LTE безразлично:
  лимит панели 0/NO_RESET, квота LTE читает `lifetimeUsedTrafficBytes`, который сброс не трогает.
* ЮKassa, CryptoBot, Telegram Stars — без изменений (fail-closed подтверждение ЮKassa — с 4.13.0).
* MulenPay, Platega — у нас не подключены. НПД: чек по покупке с лендинга — только для ЮKassa.

### 5.6 Кабинетное API (бэкенд; фронт — отдельный репозиторий, парный кабинет 1.79.0)

### 6.2 Кого из наших это задевает

* **Сетевые подписки с тарифом — нет.** Тариф ставят и покупка (`7/8/9/10`), и перенос старых
  прав: `import_legacy_quota` пишет технический тариф Wi-Fi + LTE
  (`lte_quota_service.py:548-549`). Меню, пакеты LTE в кабинете и покупка LTE идут прежним
  путём — закреплено тестом `a942e65e` (§6.4).
* **Перенесённые legacy-права и автопродление legacy (`a21c7c55`) — нет.** Это те же подписки
  с техническим тарифом; `autopay_blocked_by_legacy` читает леджер и стоит после
  апстримовского пропуска подписок без тарифа (тот был и раньше).
* **`lte_orphan_quotas` — нет.** У «сирот» нет строки подписки, правило к ним не применяется.
* **Сетевые подписки без тарифа — да, но функций они не теряют.** Появиться могут
  через пробный путь: `initialize_trial_quota` (`lte_quota_service.py:927`) ставит триалу
  `network_category='wifi_lte'`, а тариф у триала может быть пустым (`TRIAL_TARIFF_ID=0` по
  умолчанию). Пока это триал — правило молчит; конвертация покупкой клиента ставит тариф
  (`extend_subscription(tariff_id=…)`). **Но есть штатный путь без тарифа:** админская кнопка
  «💳 Купить подписку» в карточке пользователя бота (`admin_buy_subscription_execute`,
  `handlers/admin/users.py:5005`) — классическая покупка: пишет срок напрямую, снимает
  `is_trial`, тариф не ставит, леджер не трогает (так было и до 4.14). Плюс погашенный чужой
  триал и ручные правки. **Докупки LTE у такой подписки не было и
  до 4.14:** цена пакета берётся из тарифа (`lte.py:48-50`, `lte_topup_purchase_service.py:101-103`),
  без тарифа бот не показывает пакетов, кабинет отдаёт `[]`, покупка падает в леджере. Теперь
  кабинет отвечает `tariff_required` раньше леджера, а «Перейти на тариф» ведёт в нашу
  заглушку → витрину → платную смену (`is_paid_tariff_switch` пропускает managed→managed) —
  рабочий путь, которого в кабинете раньше не было.
* **Классические подписки без тарифа — ДА.** По леджеру на 04.09: **21 активная** («безлимиты
  и нераскладываемые объёмы», ручной разбор) и **1047 старых**, в основном давно истёкших.
  Теряют классические докупки трафика и устройств (если они включены в `.env`) и видят
  «Перейти на тариф» вместо продления. Продления и автоплатежа у них не было и до слияния.

### 6.3 🔴 Живая классическая подписка без тарифа упирается в тупик

Все продаваемые тарифы у нас сетевые, а форк запрещает переводить живую несетевую платную
подписку на сетевой тариф до конца срока (`validate_subscription_transition`,
`lte_quota_service.py:296-320`: «Сначала необходимо сохранить оплаченные остатки старого
тарифа при миграции»). Путь клиента: «Перейти на тариф» → список (теперь без отказов «смена
выключена» и «подписка истекла») → период → `confirm_tariff_switch` →
`validate_user_tariff_purchase` (`tariff_purchase.py:4087`) бросает `LtePolicyError` **до
списания** → общий `except` → «❌ Произошла ошибка при переключении тарифа» (`:4272`). **Денег
не берёт**, но и причины не объясняет. До слияния тот же тупик стоял за «Продлить → Выбрать
тариф»; теперь это единственная кнопка, и ранние отказы её больше не перехватывают. После
окончания срока путь работает: проверка пропускает, `extend_subscription(tariff_id=…)` →
`_prepare_donbaton_subscription` → `update_entitlement`.

В коде слияния это **не исправлялось** — продуктовое решение за владельцем:
(а) перенести эти подписки в новый учёт оператором до выкладки; (б) дать им доработать срок;
(в) небольшой патч форка: в `confirm_tariff_switch` показывать текст `LtePolicyError`, как это
уже делает кабинет, вместо общей ошибки. Рекомендую (в) отдельной задачей вместе с (а) или (б).

### 6.4 Нужна ли правка форка, чтобы сетевые подписки не считались «старыми» — нет

У сетевых подписок с тарифом правило не срабатывает. Исключить из правила сетевые подписки
без тарифа значило бы вернуть им «Продлить», ведущее в тупик (без тарифа нечего продлевать,
кабинет отдаёт пустой список периодов), и спрятать рабочий путь «Перейти на тариф» → витрина.
Докупок LTE это не вернуло бы: без тарифа их нет.

Правка кода не нужна; инвариант закреплён сторожевым тестом **`a942e65e`**
(`tests/donbaton/test_legacy_rule_keeps_network_lte.py`, 7 тестов): сетевая подписка с тарифом
не «старая» — в меню «Продлить», «Автоплатёж» и «Докупить LTE», кабинет отдаёт пакеты LTE и
доводит покупку до леджера; в боте LTE-ветка стоит раньше апстримовского отказа (с тарифом и
без); без тарифа кабинет отвечает `tariff_required`, не доходя до леджера. Проверено
мутацией: отказ апстрима раньше LTE-ветки или «старая» при любом тарифе роняют 6 тестов из 7.

### 6.5 SQL для ядра (не запускался — только текст)

Выполнять на боевой БД бота только чтением, через обёртку с одним ControlMaster-сокетом
(`local-ops/_claude/tools/donbaton-autopay-20260916/dbcore_ssh_cm.sh`) и файлом через `--put`
(кавычки в однострочниках ломаются, см. README `donbaton-u4130-20260917`).

```sql
-- 1. «Старые» по правилу 4.14.0: платные без тарифа, по статусу, категории сети и сроку
SELECT s.status,
       s.network_category,
       (s.end_date > now())      AS live_by_date,
       s.autopay_enabled,
       count(*)                  AS subscriptions,
       count(DISTINCT s.user_id) AS users
FROM subscriptions s
WHERE s.tariff_id IS NULL
  AND s.is_trial IS NOT TRUE
GROUP BY 1, 2, 3, 4
ORDER BY 1, 2, 3, 4;

-- 2. Кого задевает прямо сейчас: живые (их клиенты увидят «Перейти на тариф» и тупик §6.3)
SELECT s.id, s.user_id, s.status, s.end_date, s.traffic_limit_gb, s.device_limit,
       s.network_category, (q.subscription_id IS NOT NULL) AS has_lte_quota
FROM subscriptions s
LEFT JOIN lte_quotas q ON q.subscription_id = s.id
WHERE s.tariff_id IS NULL
  AND s.is_trial IS NOT TRUE
  AND s.status IN ('active', 'limited')
  AND s.end_date > now()
ORDER BY s.end_date;

-- 3. Сетевые без тарифа (их даёт админская «Купить подписку» по триалу; каждую — разобрать)
SELECT count(*) FROM subscriptions
WHERE tariff_id IS NULL AND network_category IS NOT NULL AND is_trial IS NOT TRUE;
```

### 7.2 Дублирует ли `0127` нашу `0126` — нет

Они пишут в **противоположные стороны** и в **непересекающиеся строки**:

| | `0126` (4.13, на проде с 17.09) | `0127` (4.14, новая) |
|---|---|---|
| Пишет | `subscriptions.remnawave_id` | `users.remnawave_id` |
| Откуда | из `users.remnawave_id` | из `subscriptions.remnawave_id` |
| Кому | у человека id **есть**, подписка ровно одна, id не держит другая строка, не черновик триала | у человека id **нет**, по всем его подпискам ровно один различный id, этот id не записан другому человеку |

`0126` требует `users.remnawave_id IS NOT NULL`, `0127` трогает только `users.remnawave_id IS
NULL` — одна строка не может попасть в обе; итог не зависит от порядка, повтор — no-op.
Проверено двумя способами: ad-hoc на SQLite (тексты обеих миграций, 9 сценариев, оба порядка)
и на PostgreSQL 16 в репетиции (§7.5). У апстрима тот же порядок (`0124` → `0125`).

### 7.3 Что делают с боевыми данными

* **`0127` — единственная, что трогает данные.** Одна `UPDATE users`, без DDL; уникальность
  `ix_users_remnawave_id` не нарушится (сторож «id не записан другому» + частично уникальный
  `uq_subscriptions_remnawave_id` не даёт одному id быть у двух подписок). Ожидание на проде —
  **около нуля строк**: одиночный режим пишет обе колонки, а `0126` 17.09 закрыла NULL у
  подписок (2137 → 0 из 2304, `STATE.md`). Кандидаты могут остаться там, где id человеку снял
  бот, а у подписки не снял: **`force_cleanup`** (`remnawave_service.py:2956`) обнуляет
  `users.remnawave_id`, но `sub.remnawave_id` не трогает — `0127` вернёт такому человеку id
  удалённого аккаунта. Вред ограничен: первое же обновление получит 404 и для живой подписки
  пересоздаст аккаунт (`recreate_deleted_panel_user`); рантайм 4.14 делает то же самое через
  `should_create_panel_account` и без миграции. Число кандидатов посчитать на копии (§11, п. 2).
* **`0128`** — `ADD COLUMN` nullable, данные не трогает.
* **`0129`** — две новые таблицы с индексами и одна строка `link_auth_method` (`is_active=false`).

### 7.4 Откат схемы

`downgrade 0126` новым образом: `0129` сносит обе таблицы напоминаний (с настройками и
состоянием по людям), `0128` — колонку, **`0127` — `pass`**: дописанные `users.remnawave_id`
остаются. Для кода 4.13 это безвредно (то же значение, что он взял бы сам), но «схема 0126» ≠
«данные как до выкладки». Если нужны прежние данные — только дамп.

### 7.5 Локальная репетиция (PostgreSQL 16.2, синтетика — не копия прода)

Схема базы `465f26e6` через `create_all` + `stamp 0126`, 9 людей и 11 подписок со всеми
сценариями `0126/0127`:

* `upgrade head` кодом слияния: `0126 → 0127 → 0128 → 0129`; `0127` дописала id ровно двум
  людям (однозначные случаи), неоднозначные и «чужой id» пропущены; колонка и таблицы на месте,
  встроенная запись одна и выключена;
* повторный `upgrade head` — no-op;
* `downgrade 0126` — 3 шага, таблицы и колонка сняты, `users.remnawave_id` остался, строки
  `withdrawal_requests` целы; повторный `upgrade head` проходит;
* **старый код (`465f26e6`) на схеме `0129`:** `Can't locate revision identified by '0129'` —
  подтверждает crash-loop при «просто вернуть старый образ» (§12); после `downgrade 0126` новым
  кодом старый проходит.
